# The b-side — Shareable League Dashboard — Campaign Design

## 1. What this is

**the b-side** is a public, no-auth, read-only micro-site — **one per league** —
hosted on `digest.mattmariani.com`. It's the fan-facing flip side of the operator app
(`mlbot2.mattmariani.com`): league members get a link, never the league HQ. Tone is
**Spotify Wrapped × high-school yearbook** — warm, a little roast-y, screenshot-bait,
never a brutal leaderboard.

This is a **campaign** (multi-sprint), decomposed below. Claude Design delivered two
detailed handoff packets covering the *presentation* and the *operator controls*; this
spec covers the campaign decomposition and the **read-model generator** (Sprint 31) —
the piece the packets assume exists but mostly doesn't.

**Design handoff references (staged in repo):**
- `docs/design/dashboard/` — the public b-side site (HANDOFF-README.md, IMPLEMENTATION-PROMPT.md, the `.jsx`/`.css` reference, `the b-side - League Dashboard Preview.html`).
- `docs/design/content/` — the operator Content screen (HANDOFF-README.md, IMPLEMENTATION-PROMPT.md, reference + `Music League Bot - Content Screen.html`).

## 2. Campaign decomposition (sprints)

The handoff packets are presentation + operator chrome. An audit (2026-06-14) shows
~80% of the read-model *content* is unbuilt — superlatives, KPIs, moments, biggest
fan/hater, discovery playlist, member tiers, spectrum, overlap-v2. That generator is the
real bulk and the creative heart, and it gates everything else. So:

- **Sprint 31 — Read-model generator + foundation** *(this spec)* — schema, slug minting,
  and the analysis/LLM tasks that produce the entire read-model per league. The make-or-break
  creative work. Builds on the sprint-28 prediction harness.
- **Sprint 32 — The public b-side site** — the 3 routes from `docs/design/dashboard/`,
  static-generated on publish, hosted on `digest.mattmariani.com`. (Handoff fully specs the UI.)
- **Sprint 33 — The operator Content screen** — `docs/design/content/`: Digest→Content tabs,
  archive list, refresh/hold/lock update modal, reshare. (Handoff fully specs the UI.)
- **Capstone (separate, after) — Universal Share button** — owner's reusable share control
  across the app, reusing the same host pipeline. Its own spec.

## 3. Locked decisions (owner, 2026-06-14)

1. **Spectrum sliders** (Polished↔Raw, Sunny↔Melancholy, Familiar↔Obscure) — **derived by
   the LLM from the player's history/fingerprint** for v1 (no precise audio features needed);
   upgrade to real audio data later when the song-metadata item lands.
2. **Hosting** — **static-generate on publish**: render the site to static files (SPA bundle +
   per-league `read_model.json`) into the existing `DIGESTS_DIR`, served by the same dumb static
   host as digests (`digest-static` caddy). Fully cacheable, no app dependency at view time.
   Mirrors the existing digest html-share model.
3. **Overlap v2** (Vote Together within shared rounds + Taste Twins across leagues) — **built in
   Sprint 31** as part of the read-model generator (also a standalone backlog item; done here, once).

## 4. What already exists (reuse — do not rebuild)

- **Taste Fingerprint** (sprint-28, `player_profiles.taste_fingerprint`) — signature artists /
  genres / eras / rewards / punishes. Feeds the profile fingerprint AND the derived spectrum directly.
- **Prediction harness** (`$lib/predict` — PredictionTask, runPrediction, buildPlayerContext,
  prediction_runs) — the substrate for every new LLM analysis task in Sprint 31.
- **Digest html-share host pipeline** (`export.ts` HtmlShareResult; `digest_shares` slug table;
  `DIGESTS_DIR` static volume → `digest.mattmariani.com/d/<slug>`) — the hosting/slug model to mirror.
- **Digest artifacts** per round — the b-side archive deep-links to these at `/{slug}/archive/{roundId}`.
- **WhatsApp bridge** — for the operator reshare step (Sprint 33).
- **v1 overlap** (global Jaccard, `playerHistory.ts`) — REPLACED by overlap v2; do not extend it.

# Sprint 31 — Read-model generator + foundation

## 5. Goal

Produce, per league, the complete **read-model JSON** the public b-side serves — generated
offline (never at request time), persisted, and (re)generated by an explicit publish/update
call. No public site, no operator UI in this sprint — just the schema, the generator, the
overlap-v2 metric, and a first-publish entry point. Output validated against the read-model
shape in `docs/design/dashboard/ml-dashboard-data.jsx`.

## 6. Schema (idempotent boot migrations, house pattern)

Per the operator handoff §8:
```sql
CREATE TABLE dashboard_sites (
  slug            TEXT PRIMARY KEY,          -- unguessable ≥80-bit token, minted on first publish
  league_id       INTEGER NOT NULL UNIQUE,   -- one site per league (our leagues are integer-keyed)
  season          INTEGER NOT NULL,
  read_model      TEXT NOT NULL,             -- JSON snapshot the public site serves as-is
  archived_rounds TEXT NOT NULL DEFAULT '[]',-- JSON array of round ids already in the archive
  is_live         INTEGER NOT NULL DEFAULT 1,
  published_at    TEXT NOT NULL,
  refreshed_at    TEXT NOT NULL
);
CREATE TABLE dashboard_section_state (
  league_id INTEGER NOT NULL,
  section   TEXT NOT NULL,   -- 'superlatives'|'stats'|'fingerprints'|'moments'|'overlap'|'playlist'
  decision  TEXT NOT NULL DEFAULT 'refresh',  -- 'refresh'|'hold'|'lock'
  steer     TEXT,            -- last steer chips+instructions for this section
  PRIMARY KEY (league_id, section)
);
```
(Slug ≥80 bits, capability-URL style. `read_model` mirrors `ml-dashboard-data.jsx`.)

## 7. The read-model generator — `$lib/dashboard/`

A `buildReadModel(db, leagueId, opts) → ReadModel` that assembles the full per-league snapshot.
Sub-generators, each a focused unit (LLM ones run on the prediction harness, logged to
`prediction_runs`; deterministic ones are pure SQL/compute):

| Read-model piece | Kind | Source |
|---|---|---|
| `league` meta | deterministic | leagues/seasons/rounds tables |
| `members[].fingerprint` (artists/genres/eras/rewards/punishes) | reuse | sprint-28 `taste_fingerprint` (generate if missing) |
| `members[].spectrum` (3 axes) | **LLM** | derived from the player's fingerprint+history (decision §3.1) |
| `members[].superlatives` + `signatureSuperlative` | **LLM** | per-player yearbook awards from history; warm/no-strife (§9) |
| `members[].biggestFan` / `biggestHater` | deterministic + LLM blurb | asymmetric vote relationships (who rewards/withholds points); hater is *friendly* (amber) |
| `members[].voteTogether[]` / `voteTwins[]` | **overlap v2** | §8 |
| `members[].playlist` | **LLM** | personality-driven discovery playlist + one-line "agenda" |
| `members[].tier` (full/lite) | deterministic | activity threshold rule (e.g. submissions/rounds played) |
| `members[].stat` (submitted/avg/wins) | deterministic | gameplay tables |
| `reel[]` (league superlatives) | **LLM** | league-wide awards |
| `kpis[]` (celebratory facts) | deterministic + LLM phrasing | NO win/loss ladder (§9) |
| `moments` (mostLoved/mostDivisive/biggestUpset) | deterministic + LLM line | vote spread per round |
| `archive[]` | deterministic | finalized rounds → digest artifacts |

Each LLM sub-generator is its own `PredictionTask` (template + zod output schema) so it's
testable with a stubbed `callOpenRouter` and tunable. Accent values restricted to
`pulp|amber|sky|moss|ember`.

## 8. Overlap v2 (also fulfills the standalone backlog item)

Two separately-labeled metrics, both precomputed into the read-model:
- **Vote Together** (within shared rounds) — of songs both players could actually vote on
  (rounds they both played), how often they hand each other points. Behavioral. Players with
  zero shared rounds are omitted (not shown as a fake low %).
- **Taste Twins** (across all leagues) — taste similarity from the fingerprints (shared
  signature artists/genres/rewards), independent of shared rounds — no penalty for no overlap.

Replaces the v1 global-Jaccard `tasteOverlap`. (The operator Player Research overlap UI can
adopt these later; in-scope here is the read-model computation + the data.)

## 9. The "fun" / no-strife contract (quality bar — from the handoff §6)

The generator must encode this, since the words are generated here:
- **KPIs = celebratory facts, never a ladder.** "9 different round winners", "1994 is the
  league's favorite year". NEVER last-place / worst-average / win-loss records.
- **Superlatives are warm** — even spicy ones land as affectionate ("Most Likely to Clear the
  Room"), friendly-ribbing dialed as a compliment.
- **Biggest Fan / Friendly Hater** — the "hater" is explicitly friendly (amber, not ember/red);
  the person who most often withholds points or used a rare downvote, framed lovingly.
- **Moments** = group consensus (most loved / most divisive / quiet upset), not individual rankings.
LLM prompts carry these as hard constraints; this is make-or-break and worth an eval pass.

## 10. First-publish entry point

A `publishSite(db, leagueId) → { slug }` that: mints a permanent ≥80-bit slug (stored in
`dashboard_sites`), runs `buildReadModel` over all finalized rounds, persists the read_model +
`archived_rounds`. Idempotent re-publish refreshes in place on the same slug. Exposed as
`POST /api/content/:leagueId/publish` (the operator UI in Sprint 33 calls it; in Sprint 31 it's
callable/testable directly). The incremental update flow (refresh/hold/lock per section) is
Sprint 33's `POST /api/content/:leagueId/update` — but `buildReadModel` is written section-wise
now so that update can reuse it.

## 11. Non-goals (Sprint 31)

- No public site rendering (Sprint 32) and no operator UI (Sprint 33).
- No real audio-feature spectrum (derived from fingerprint per §3.1).
- No incremental refresh/hold/lock modal (Sprint 33) — but the generator is section-wise so it slots in.
- No WhatsApp reshare (Sprint 33).

## 12. Testing / success

- Schema boots idempotently; both tables present.
- `buildReadModel(db, leagueId)` returns an object validating against the `ml-dashboard-data.jsx`
  shape; every LLM sub-generator has a vitest with a stubbed `callOpenRouter`; deterministic
  sub-generators (overlap v2, KPIs, stats, tiers, archive) have data-driven vitests.
- `publishSite` mints a slug, persists a read_model, and re-publish reuses the slug.
- Overlap v2: a player with zero shared rounds is omitted from Vote Together but can appear in
  Taste Twins; a known co-voting pair scores high in Vote Together.
- A `lite`-tier member's read-model omits the sections it lacks (no empty blocks).
- `npm run check` 0 errors; `npx vitest run` green.
- **Quality spot-check (manual):** generate a real league's read-model and eyeball superlatives /
  KPIs / fan-hater for the no-strife bar before Sprint 32 consumes it.

## 13. Open questions (resolved unless noted)

- Spectrum / hosting / overlap-v2 → RESOLVED (§3).
- League/member id types: our leagues + players are integer-keyed; the fixture uses string ids —
  map at the read-model boundary (string ids in JSON are fine; keep DB joins integer).
- **OPEN (minor, defer to plan):** the exact `tier` full/lite threshold rule (pick a simple,
  defensible activity cutoff at plan time).
- **OPEN (minor):** member-id stability in slugged URLs (`/p/{memberId}`) — use the stable
  `player_id`, not name.
